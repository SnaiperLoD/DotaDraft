## Что сделано хорошо

### 1. Проект действительно модульный

Бэкенд разделён на самостоятельные Nest-модули:

- Draft;
- Evaluation;
- Battle;
- Captains;
- TI Run;
- History;
- Auth;

Это хороший modular monolith: для текущего масштаба микросервисы были бы дорогим цирком без зрителей.

### 2. Два хранилища используются осмысленно

SQLite хранит локальное состояние:

- героев;

- историю;
- результаты боёв;
- пользователей;
- TI Runs;
- Captains sessions.

PostgreSQL используется только там, где действительно нужно общее состояние между игроками:

- пул соперников;
- глобальные результаты;
- лидерборд.

Для friends-alpha это разумный компромисс.

### 3. Тестовая культура сильно выше среднего

Проверенный release-gate:

- 583 server unit-теста;
- 27 client unit-тестов;
- всего 610 успешно пройденных unit-тестов.

В репозитории также есть:

- integration suite;
- Playwright e2e;
- responsive screenshot tests;
- mutation testing через Stryker;
- проверки Battle, Evaluation, ролей, тегов, auth, TI и Captains.

Особенно хорошо покрыта самая рискованная часть — игровой и аналитический core.

### 4. CI не декоративный

GitHub Actions проверяет:

- build;
- lint;
- formatting;
- TypeScript;
- server unit;
- client unit;
- integration;
- Playwright;
- Docker Compose build.

Это полноценный quality gate, а не зелёный badge ради красивой жизни.

### 5. Security basics адекватны масштабу

У проекта есть:

- `scrypt` для паролей;
- timing-safe comparison;
- HttpOnly session cookies;
- Secure cookies в production;
- SameSite;
- ограничение размера JSON;
- write rate limiting;
- выключение debug-модулей в production;
- CORS-конфигурация;
- token-gated чтение телеметрии.

Для публичного SaaS этого недостаточно.

Для solo friends-alpha — нормально.

### 6. Есть graceful degradation

Недоступность общего PostgreSQL-пула не убивает всё приложение.

Evaluation и локальные сценарии продолжают работать, а health endpoint сообщает degraded-состояние.

Это зрелое продуктовое решение.

## Главные архитектурные проблемы

### 1. Evaluation и Battle фактически сцеплены

По продуктовой доктрине это два разных движка:

- Evaluation объясняет качество драфта;
- Battle оценивает конкретный матчап и разыгрывает исход.

В коде граница уже размыта:

- Evaluation импортирует axis math из Battle;
- Evaluation использует форматирование и правила custom tags;
- Battle импортирует классификацию архетипа из Evaluation.

Пока это не катастрофа.

Но дальнейшая калибровка одного движка будет всё чаще случайно менять другой.

**Что делать:** вынести общий чистый слой:

`assessment-core`

В нём оставить:

- типы осей;
- role-aware значения;
- feature extraction;
- общие математические функции.

Evaluation и Battle должны зависеть от него, но не друг от друга.

### 2. Аналитика, объяснения и game rules живут в одном расчёте

Сейчас рядом находятся:

- оценка силы;
- статистические matchup-данные;
- custom tags;
- hidden calibration tags;
- confidence tiers;
- случайный игровой outcome;
- narrative.

У этих частей разные задачи и разные критерии качества.

Их необходимо развести:

1. `OutcomeModel` возвращает вероятность.
2. `ExplanationPolicy` объясняет вклад факторов.
3. `GameResolver` добавляет игровой рандом и authored mechanics.
4. UI только отображает результат.

### 3. Конфигурация загружается слишком рано

Часть JSON-конфигов читается при импорте модулей.

Из-за этого исследовательские скрипты:

- временно переписывают файлы;
- запускают дочерний процесс;
- восстанавливают файлы в `finally`.

Это хрупко:

- сбой процесса может оставить изменённый конфиг;
- кеш импортов мешает экспериментам;
- параллельные запуски небезопасны;
- воспроизводимость зависит от порядка запуска.

**Что делать:** передавать immutable config object в движок явно.

Ни один эксперимент не должен переписывать production JSON.

### 4. Контракты API синхронизируются не полностью

Часть типов находится в `shared`, но `DraftStateView` определён отдельно на сервере и клиенте.

Из-за этого:

- сервер считает `createdAt` объектом `Date`;
- клиент считает его строкой;
- статус типизирован с разной строгостью;
- TypeScript не гарантирует совпадение HTTP-контракта.

**Что делать:** вынести wire-format DTO в `shared`.

### 5. JSON хранится строками в SQLite

Это удобно для MVP, но создаёт долг:

- нет DB-level validation;
- много ручного `JSON.parse`;
- сложнее делать запросы;
- формат может незаметно разъехаться;
- миграции данных становятся ручными.

Сейчас переписывать всё не нужно.

Нужны:

- schema/version внутри важных payload;
- централизованный parse/validate;
- миграционная стратегия для сохранённых Evaluation и Battle results.

## Операционные ограничения

### Проект рассчитан на один API instance

В памяти процесса хранятся:

- rate-limit buckets;
- временные Google OAuth states;
- in-flight Battle promises;
- некоторые кеши.

После рестарта OAuth flow может потеряться.

При двух API replicas состояние разойдётся.

Это нормально, если deployment явно фиксирует:

**один экземпляр API**.

Если появится масштабирование — временное состояние нужно вынести в Redis или БД.

### Persistence местами best-effort

Некоторые ошибки сохранения логируются, но не ломают пользовательский запрос.

Плюс:

- бой не падает из-за временного сбоя истории или лидерборда.

Минус:

- пользователь может увидеть результат, который не появился в History;
- W/L соперника может не обновиться;
- UI не сообщает о частично сохранённом состоянии.

Для Evaluation это приемлемо.

Для Battle history и leaderboard нужен явный статус сохранения или retry/outbox.

## Что обнаружилось при локальной проверке

### Unit release-gate прошёл

Успешно:

- shared build;
- client tests;
- server unit tests.

Результат: **610 тестов прошли**.

### Full build на Windows столкнулся с Prisma lock

`prisma generate` пытался заменить:

`query_engine-windows.dll.node`

Файл удерживался запущенным Node-процессом.

Это не TypeScript-ошибка приложения, но реальный DX-footgun:

- `npm run build` всегда повторно генерирует Prisma clients;
- build нельзя безопасно запускать рядом с dev-server на Windows.

**Решение:** отделить `prisma:generate` от обычного compile-build либо запускать генерацию только когда schema/hash изменились.

### Integration suite сломал старый `.stryker-tmp`

Jest увидел дубликаты пакетов внутри Stryker sandbox:

- `server`;
- `shared`;
- generated Prisma client.

Из-за этого integration tests не стартовали.

`eslint .` также начал обходить временные Stryker-каталоги и завис.

Это не падение бизнес-логики.

Это дефект локальной гигиены инструментов.

**Исправление небольшое:**

- добавить `server/.stryker-tmp/**` в ESLint ignores;
- добавить каталог в Prettier ignores;
- исключить его из Jest haste map;
- чистить sandbox после mutation run.

## Ты как гейм-дизайнер — 79/100

### Что хорошо

#### Основное действие соответствует фантазии продукта

Игрок не заполняет форму и не читает отчёт.

Он собирает драфт, распределяет роли и вступает в бой.

Механика напрямую выражает fantasy «я капитан команды».

#### Есть meaningful decisions

Игрок принимает решения о:

- героях;
- ролях;
- синергиях;
- покрытии слабостей;
- темпе;
- scaling;
- риске;
- сопернике;
- продолжении run.

Даже если модель несовершенна, действия игрока имеют понятный игровой смысл.

#### Хорошо сделан payoff

Battle не заканчивается сухим `Win/Lose`.

Есть:

- визуальный verdict;
- история боя;
- линии;
- сильные и слабые стороны;
- matchup cards;
- shutdown;
- архетип;
- объяснение upset.

Это превращает вычисление на сервере в игровой момент.

#### Режимы используют разные типы мотивации

Battle даёт быстрый цикл.

Captains даёт mastery и узнаваемый competitive ritual.

TI Run даёт fantasy турнира и более длинную арку.

Такое разделение показывает понимание разных player motivations.

#### Игра использует язык Dota, но не копирует матч

Оси, роли, пики, баны, стадии и matchup narrative создают узнаваемость.

При этом проект не пытается симулировать:

- каждую минуту;
- закуп;
- микроконтроль;
- карту;
- исполнение конкретных игроков.

Это правильное сокращение пространства игры.

### Что плохо

#### Скрытые calibration tags подрывают ощущение честности

Если hidden tag был добавлен потому, что конкретная группа героев плохо совпадала с реальным WR, он работает как скрытый балансный костыль.

Игрок не может вывести это правило из видимых свойств системы.

Для аналитического инструмента это проблема объяснимости.

Для игры — проблема perceived fairness.

#### High confidence фактически означает детерминированный исход

В production High tier даёт фавориту 100% базового веса победы, если отдельная игровая механика не разрешает upset.

При этом на сохранённых pro-матчах High-фаворит выигрывал около 71%.

Как game rule это допустимо.

Как слово `confidence` — вводит в заблуждение.

Нужно либо:

- переименовать tier в игровой термин;
- либо строить его из калиброванной вероятности.

#### Evaluation и Battle могут восприниматься противоречиво

Высокий Total Score не гарантирует победу, потому что:

- Evaluation оценивает состав сам по себе;
- Battle сравнивает его с конкретным соперником;
- затем применяется игровой resolver.

Это логично внутри системы.
